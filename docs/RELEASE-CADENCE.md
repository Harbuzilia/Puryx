# RELEASE-CADENCE: механика ежедневных пушей при пакетной локальной работе

> Спутник `docs/ROADMAP.md`. Отвечает на главный процессный вопрос: **как работать локально крупными заходами, но показывать на GitHub живую ежедневную историю**, а не «один коммит на 50 файлов раз в месяц».
> Требование пользователя (02.10.2026): пуш в публичный репо (github.com/Harbuzilia/Puryx, master) нарезанными кусками ~раз в сутки.

---

## 1. Модель ветвления: прямой master (выбор и обоснование)

**Выбрано: линейный `master` + атомарные Conventional-коммиты, без PR.**

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Прямой master (выбрано)** | Идеально читаемая линейная история; нулевая церемония; каждый тег указывает на понятную цепочку | Дисциплина «коммит только зелёный» на совести автора | ✅ соло-разработка публичного репо |
| Short-lived feature-ветки + merge | Изоляция WIP | Merge-коммиты шумят историю; без PR церемония бессмысленна | ❌ как основной режим |
| PR на каждый день | Видимость «в процессе» через открытые PR | Соло-мейнтейнер: PR сам себе; двойная история (branch+PR) | ❌ избыточно |

**Правила:**
- Один коммит = один смысловой шаг (`fix(...)`, `test(...)`, `docs(...)`, `refactor(...)`; без эмодзи — правило конфигурации Code Atlas).
- Коммит в `master` **всегда оставляет дерево зелёным** (см. §3). Красный WIP живёт в рабочем дереве (незакоммиченным), в `git stash` или в ветке `wip/<topic>` — но не в master.
- `wip/<topic>`-ветка допустима только для много-дневной рискованной задачи (в ROADMAP это M1, Дни 13–14): работа там коммитится как угодно, в master попадает rebase-серия атомарных коммитов (`git rebase master` → перенести по одному; merge-коммит не создаём).
- **Запрещено** после публикации: `git push --force`, rebase/правка запушенных коммитов. История публичная — переписывать нельзя.

## 2. Механика «очереди коммитов» (ядро каденции)

Идея: локальный `master` **опережает** `origin/master` на сколько угодно коммитов (сколько наработано заходом), а публикуем мы его «дневными порциями» — доводим `origin/master` до границы дня.

### Ежедневный ритуал (5 команд)

```bash
# 1) Посмотреть очередь — что уже готово, но не опубликовано
git log origin/master..master --oneline

# 2) Выбрать границу дня: последний коммит, относящийся к СЕГОДНЯШНЕЙ задаче ROADMAP
#    (граница = SHA последнего коммита дня; дни в ROADMAP размечены по задачам)
git log origin/master..master --oneline | findstr /n .   # пронумеровать, SHA слева

# 3) Прогнать дневной гейт ИМЕННО на границе (если работа уже убежала дальше)
git worktree add ..\puryx-verify <SHA>
cd ..\puryx-verify && dotnet build SmartCleaner.sln -c Release && dotnet test SmartCleaner.sln -c Release
cd <основной чекаут> && git worktree remove ..\puryx-verify

# 4) Опубликовать порцию: довести origin/master до границы (быстрый форвард)
git push origin <SHA>:refs/heads/master

# 5) Убедиться, что очередь дня опустела
git log origin/master..master --oneline
```

Если работа дня закончена и дальше ничего не наработано — шаги 3–4 вырождаются в обычные:
```bash
dotnet build SmartCleaner.sln -c Release && dotnet test SmartCleaner.sln -c Release
git push origin master
```

**Почему пуш по SHA работает:** `git push origin <SHA>:master` перемещает удалённую ветку до этого коммита, если это быстрый форвард (а он быстрый — локальная история линейная и только растёт вперёд). Так «нарезается» любой уже закоммиченный backlog без переписывания истории.

**Норма порции:** 1–4 коммита, суммарно ≤ ~500 строк диффа. Больше — значит день в ROADMAP слишком крупный: вернись к декомпозиции.

### Что делает границу «безопасной границей пуша»

Коммит подходит под пуш, если:
1. Он завершён смыслово (конец атомарного шага, не посреди правки).
2. Дневной гейт на нём зелёный (см. §3).
3. На нём **нет** WIP-состояния (незакоммиченные файлы в пуш не попадают — это плюс модели).

Гарантия практикуется так: коммитим в master только проверенное; тогда ЛЮБОЙ коммит — потенциальная граница, и пуш по SHA не требует особой аккуратности.

## 3. Правила дня: «пушабельный» vs «непушабельный»

**День пушабельный, если на границе:**
```
dotnet build SmartCleaner.sln -c Release    # 0 ошибок / 0 предупреждений
dotnet test SmartCleaner.sln -c Release     # все зелёные (число не меньше вчерашнего)
```
Прогонять на пушимом SHA (worktree из §2), а не на последнем наработанном.

**Если день непушабельный (красная сборка/тесты, задача не сошлась):**
- Код **не пушим**. WIP остаётся локально (stash/wip-ветка/незакоммиченный).
- Допустим честный минимальный пуш активности: только doc-коммиты (заметки о ходе дня в ROADMAP/CHANGELOG) — это правда отражает работу, не имитирует результат.
- Пропуск дня — нормально (см. §6). Не наверстывать пачкой «3 дня за один вечер»: порция >4 коммитов ломает читаемость и весь смысл каденции.

**Против фальши:** не пушим «пустой» коммит ради галочки; не дробим осмысленный коммит на 5 искусственных (атомарность = смысл, не количество).

## 4. Ритм документации (сцеплен с каденцией)

Каждый день-пуш заканчивается одним doc-коммитом:
```
docs(day): закрыть День N — <задача>
```
содержание: отметить `- [x]` выполненные пункты дня в `docs/ROADMAP.md` **и** дописать 1–3 строки в секцию `## [Unreleased]` файла `CHANGELOG.md` (черновик release notes — требование пользователя). На релизных днях (16, 29) Unreleased сворачивается в секцию версии.

Так `CHANGELOG` сам накапливает черновик релиза, а история GitHub показывает непрерывную осмысленную активность: код + журнал.

## 5. Релизные точки (только milestone)

Теги и GitHub Releases — **только** в точках ROADMAP: `v2.7.3` (опционально, P0-хотфикс), `v2.8.0` (День 16), `v3.0.0` (День 30). Ежедневные пуши НЕ тегируются.

**Чек-лист релиза (дни 16 / 29–30):**
```bash
# 1. Версия: csproj (Version/AssemblyVersion/FileVersion) + бейдж README совпадают
# 2. CHANGELOG: секция [X.Y.Z] оформлена из Unreleased
# 3. Гейт зелёный на релизном коммите
dotnet build SmartCleaner.sln -c Release && dotnet test SmartCleaner.sln -c Release
# 4. Тег аннотированный, пуш тега
git tag -a vX.Y.Z -m "Puryx vX.Y.Z"
git push origin vX.Y.Z
# 5. Portable-артефакт
publish_portable.bat    # release\portable\SmartCleaner.App.exe
# 6. GitHub Release: notes из CHANGELOG, приложить exe, publish
# 7. reviewer-верификация: релиз открывается, артефакт скачивается и запускается
```
Порядок гарантирует: тег всегда указывает на зелёный коммит; артефакт релиза собран из тега (перед сборкой `git checkout vX.Y.Z` в отдельном worktree, если работа уже убежала вперёд).

## 7. Опция: автоматизация через OpenChamber schedule

Ежедневный ритуал из §2 можно поручить запланированной задаче OpenChamber (создаётся пользователем/координатором один раз; сейчас НЕ создана — это опция):

- **Action:** `schedule.create`
- **Параметры:** `name: "Puryx — ежедневный пуш"`, `daily: "19:00"`, модель — кодовая по умолчанию, `prompt:` (ниже), включён сразу.
- **Промпт задачи (шаблон):**
  > Ты — дежурный по пуш-каденции Puryx (E:\AllMyProject\CHISTilka). Работай строго по docs/RELEASE-CADENCE.md: 1) `git log origin/master..master --oneline` — очередь; 2) определи границу сегодняшнего дня по docs/ROADMAP.md (следующий незакрытый день); 3) прогони гейт (build+test) на границе через отдельный worktree; 4) если зелёное — `git push origin <SHA>:refs/heads/master`, отметь чекбоксы дня в ROADMAP и допиши строки в CHANGELOG [Unreleased] одним doc-коммитом, запушь его; 5) если красное или очередь пуста — ничего не пушь, верни отчёт одной строкой. Не делай кодовых правок.

- **Границы ответственности автомата:** он публикует уже готовое и зелёное, ведёт doc-журнал, но не пишет код и не решает, «что считать днём» — это размечено в ROADMAP.
- **Риск опции:** автомат пушит без человеческой проверки содержимого → перед включением прогнать неделю вручную по §2; промпт жёстко ограничен «push only if green».
- Отключается `schedule.toggle`, ручной запуск вне расписания — `schedule.run`.

## 8. Границы (что НЕ входит в каденцию)

- Сила истории: никакого force-push и переписывания опубликованных коммитов.
- Никаких релизов/тегов вне milestone-точек (§5).
- CI не является блокером пуша до Дня 25 (его ещё нет); после Дня 25 гейт GitHub Actions становится вторым обязательным условием «пушабельности» (красный CI = день не закрыт, фиксится на следующий день).
- Переименование неймспейсов/сборок SmartCleaner.* → Puryx.* — вне каденции: отдельное решение пользователя (сейчас зафиксировано как «исторические кодовые имена» в README).
